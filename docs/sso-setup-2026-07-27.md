# IAM Identity Center SSO Setup — 2026-07-27

Replaces interactive/local root-console sign-in and static IAM user credentials with IAM Identity Center SSO — short-lived, browser-issued temporary credentials for CLI and local script use (billing/Cost Explorer scripts, ad hoc account work).

---

## Problem

Local scripts (e.g. billing/Cost Explorer pulls) and interactive account access had no credential path that avoided either the root-user browser sign-in or a long-lived IAM user access key. The README's Known Constraints called this out directly: the account's sole IAM user (`serverless-admin`) holds `AdministratorAccess` with no MFA, scoped for CI/CD but never addressed for interactive/local use.

## Approach

IAM Identity Center (AWS SSO), using the AWS-managed built-in identity directory — no external IdP (Okta/Azure AD/etc.), so no additional cost. `aws configure sso` + `aws sso login` replace static keys with cached temporary credentials.

## What Actually Happened

Identity Center has two enablement modes that are easy to conflate:

- **Account instance** — standalone, scoped to a single AWS account. **Cannot assign access to AWS accounts at all** — it only supports AWS-managed application assignments (e.g. SaaS apps via SAML). This is a hard platform limitation, not a permissions issue.
- **Organization instance** — requires AWS Organizations, gives you Permission Sets + AWS account assignments (Multi-account permissions), which is what CLI/console SSO access actually needs.

First attempt enabled an **account instance** (misled by the "isolated single-account use case" framing on the enablement page). Hit a dead end at the AWS access portal: 0 accounts listed, no way to assign one. `sso-admin create-account-assignment` isn't supported against an account instance at all. Confirmed the instance was permanently locked in this mode a second way too — attempting to enable "identity-enhanced sessions" on it returned `Sharing feature is not supported for an account level instance with id ssoins-...`, i.e. not just missing a feature, structurally incompatible with what was needed.

Fix: enabled **AWS Organizations** on the account (`Trainbus`, `046685909731`) — this account becomes the Organization's management account; no other member accounts required or added, no cost. Deleted the account-instance Identity Center instance (`aws sso-admin delete-instance`), then tried recreating directly via `aws sso-admin create-instance` — that failed too: `ValidationException: Organization management account is not allowed to perform the operation` (org-instance creation isn't exposed through this CLI call against a management account). Went through the console's **Enable** flow instead — with an Organization now present, it defaulted to an **organization instance** without any extra prompting, which does support account assignments.

Also hit a second snag: initial sign-in attempts failed with *"You are required to provide multi-factor authentication (MFA) that you do not have"* — this fired even for a brand-new user with no prior state, including during password reset itself. Two things were changed in parallel while chasing this, so which one actually mattered isn't fully isolated: (1) the instance-level **Authentication → Multi-factor authentication → "Prompt users for MFA"** setting, which the console UI showed as saved to "Never" but had silently reverted to "context-aware" on reload — required a second visit, re-apply, and a page reload to confirm it actually stuck this time; and (2) the user itself was deleted and recreated from scratch (new `UserId`, account assignment redone against it) partway through, in case the first user object had picked up some bad state. Login succeeded only after both had happened — worth knowing if this recurs, since the setting-persistence bug alone may or may not have been sufficient.

## Final Setup

- **AWS Organizations**: enabled, `Trainbus` (`046685909731`) is the management account, no member accounts
- **Identity Center**: organization instance, `us-east-1`, instance `ssoins-7223d57d2f540c4c`, identity store `d-90667959c1`
- **User**: `donwuachi` (Derrick Onwuachi), created via `aws identitystore create-user`
- **Permission set**: `AdministratorAccess`, 8-hour session duration, AWS-managed `AdministratorAccess` policy attached
- **Account assignment**: `donwuachi` → `046685909731` via the `AdministratorAccess` permission set
- **MFA**: enabled — "Prompt users for MFA" set to context-aware; authenticator app device registered for `donwuachi` ("donwuachi's MFA 1 - SSO Google Auth"), confirmed working on fresh login
- **Access portal**: `https://d-90667959c1.awsapps.com/start`

## Verification

Confirmed login via AWS access portal — `Trainbus` account listed with the `AdministratorAccess` role, "Access keys" option available for CLI credential retrieval.

Confirmed local CLI access from WSL2:

```
aws configure sso
# SSO session name: platform-foundation
# SSO start URL:    https://d-90667959c1.awsapps.com/start
# SSO region:       us-east-1
# Account/role auto-selected (only one of each): 046685909731 / AdministratorAccess
# Default region:   us-east-1
# Output format:    json
# Profile name:     platform-foundation
```

```
aws sts get-caller-identity --profile platform-foundation
# → arn:aws:sts::046685909731:assumed-role/AWSReservedSSO_AdministratorAccess_.../donwuachi
```

```
aws --profile platform-foundation ce get-cost-and-usage --time-period Start=2026-07-01,End=2026-07-27 --granularity MONTHLY --metrics BlendedCost
```

Verified against a real workload, not just `sts get-caller-identity` — ran the live Cost Explorer query above through the same profile and got real billing data back, then confirmed the existing `infra_audit_cli.py bill` tool works against this profile unmodified (it already accepted `--profile` and passed it straight into `boto3.Session(profile_name=...)`) — full cost-by-service breakdown returned from inside the project's `.venv`:

```
source .venv/bin/activate
python infra_audit_cli.py bill --profile platform-foundation
```

No code changes required anywhere in the tooling — any script or CLI invocation that already accepted a named profile picks this up for free.

**Session behavior:** the `AdministratorAccess` permission set's 8-hour session duration means the cached SSO token expires after 8 hours; `aws sso login --profile platform-foundation` re-authenticates (browser approval, no password) without redoing the full `aws configure sso` setup.

**End result:** root-user sign-in is no longer needed for either interactive console work or local CLI/script use — both now go through `donwuachi` via SSO.
